## Suspects (reviewer)

**Mouse.** `Input.requestLock()` (`src/core/input.ts` about line 101)
calls `requestPointerLock({ unadjustedMovement: true })` and, only if
that returns a promise that rejects, calls plain `requestPointerLock()`
from inside the `.catch`. Check what Firefox does with the option and
with the return value (some versions return `undefined`, some a promise;
a refusal may come only as a `pointerlockerror` event). The retry in the
`.catch` runs after the click's user activation, which Firefox may
refuse. Either way the player clicks and never gets the lock.

Fix so the lock is taken inside the click in every browser: for example
ask for raw input only where it is known to work and otherwise call the
plain form directly in the click handler, and remember after one
refusal (`pointerlockerror` or a rejected promise) to use the plain form
on the next click. Keep raw input in Chrome.

**Foamers not loading.** `MesherPool` (`src/voxel/mesher-pool.ts`) posts
each job to a module worker and resolves it only from `onmessage`. There
is no `onerror` or `onmessageerror`: if a worker fails to start, throws,
or its reply cannot be cloned, the job stays pending forever, the part's
`VolumeMesh` stays `busy`, and the part is never drawn and has no
collider. Look for a Firefox-specific cause too (the module worker and
its imports, including JSON through `materials.ts`; the transfer lists in
both directions, for example a buffer listed twice or a view that is not
the whole buffer; `navigator.hardwareConcurrency`).

Fix so a part always finishes: on a worker error or a reply that does
not come, mesh that job on the main thread with `greedyMesh` (the same
call the worker makes) and log one `console.warn` naming the cause; if
the workers cannot start at all, the pool meshes everything on the main
thread. Fix the root cause as well if you find one.
